# 订单、付款单编辑页 SQL 查询审计

## 结论与范围

代码中确认存在订单详情 N+1 查询：`OrderORM.json()` 遍历付款记录时读取
`pay.payer`、`pay.payee_supplier`，原详情接口没有预加载这两项。
付款单详情会分别加载关联订单、项目、付款单位、收款单位和发票，查询次数固定但可合并。

本次只修改两个详情接口的关联加载策略，保持响应字段、金额、附件及发票关系不变。
没有改动数据库结构、生产数据或保存规则，没有部署服务器。

以下为相同后端代码在隔离 SQLite 数据库中的实测，不是线上 MySQL 日志。
每次请求前清理 ORM session，统计包含登录用户读取的全部 SQL。

| 场景 | 修改前 SQL | 修改后 SQL |
| --- | ---: | ---: |
| 订单详情，1 笔付款 | 6 | 3 |
| 订单详情，20 笔付款 | 44 | 3 |
| 订单详情，100 笔付款 | 204 | 3 |
| 单笔付款详情 | 7 | 3 |

订单样本的每笔付款使用不同的付款单位和收款单位；真实记录重复使用同一单位时，
ORM identity map 会复用已加载对象，原查询数会低于此样本，不能按付款数量机械推算线上次数。

## 修复

- 订单：主查询联接项目、供应商；付款记录用一次批量查询，同时联接付款单位、收款单位。
- 付款单：主查询联接订单及项目、付款单位、收款单位；发票仍独立批量加载，避免集合联接扩大主结果。
- 两者均为：用户读取 1 次 + 主记录及单值关联 1 次 + 集合关联 1 次。
- 保持外联接语义，历史记录缺少关联项目、单位时仍能正常返回。

## 其余编辑请求

| 接口 | 本次测试 SQL 次数 |
| --- | ---: |
| 项目选项 `/project/?mode=slim` | 每页 3 |
| 订单选项 `/order/?mode=options` | 非空且有项目时每页 5 |
| 供应商选项 `/supplier/?mode=slim` | 每页 3 |
| 付款单位 `/payer/` | 每页 3 |
| 材料、付款状态字典 | 各每页 2 |
| 保存订单（修改金额并校验供应商） | 4，含 UPDATE |
| 保存付款（修改金额，空发票关联） | 6，含 UPDATE |

在选项均只有一页、不打开关联发票选择器时，修复后完整打开订单编辑约 11 次 SQL，
付款单编辑约 18 次 SQL，分布在多个并行 HTTP 请求中。
保存样本不能代表所有附件、发票增删情形；未发现保存操作存在按历史付款条数增长的查询。
保存后返回工作台还会单独发起列表刷新，不能将这部分耗时混同为数据库提交耗时。

前端仍使用 `allRows` 拉取下拉数据的全部分页。项目、订单或供应商超过单页数量时，
SQL 和网络请求仍会随页数增加；需要结合服务器真实数据量判断是否改为远程搜索。

## 验证

38 项相关后端测试通过。新增回归覆盖 100 个不同付款/收款单位、金额合计、
附件、发票税额、空关联、记录不存在和未登录请求。
本地现有数据库也运行了只读诊断，各详情接口均测到 3 次 SQL。

## 服务器实测

将 `scripts/profile_editor_queries.py` 放到服务器对应项目目录后运行：

```bash
cd /root/pear-admin-flask
docker exec -w /app pear_admin_web python scripts/profile_editor_queries.py --config prod --repeat 2
```

可附加 `--order-id 具体订单ID --payment-id 具体付款单ID`，否则各取最新一条。
脚本只执行 GET/SELECT，不启动应用定时任务、不执行迁移、不输出业务记录或凭据。
输出 SQL 次数、SQL 执行耗时、接口总耗时、返回字节数、总行数和需要加载的分页数。
它测量容器内当前源码与数据库，不包含浏览器、网络、Nginx 或 Gunicorn 排队时间；
因此还需核实运行中的工作进程版本，不能只凭脚本结果宣称线上页面已恢复。
